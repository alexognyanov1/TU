# Упражнение 2: Нишки в C++

**Стандарт и компилатор:** C++17. Компилиране:

```bash
g++ -std=c++17 -Wall -Wextra -pthread -o prog prog.cpp
```
## Теоретична част

### 1. Създаване на нишки

Нишката е поток от изпълнение вътре в един процес. Всички нишки на процеса споделят едни и същи глобални променливи и купчина (heap), но всяка има собствен стек. Във всяка програма има поне една нишка - тази, която изпълнява `main()`.

В C++ нишка се създава с класа `thread` (заглавен файл `<thread>`). На конструктора се подава функция (или lambda), която нишката да изпълни, и нейните аргументи. Нишката стартира веднага след създаването. Главната нишка трябва да извика `join()`, за да изчака другата да завърши. Ако обект `thread` бъде унищожен, без да е извикан `join()` (или `detach()`), програмата се прекратява аварийно.

**Основни средства:**

- `thread t(функция, аргументи...)` - създава и стартира нишка
- `t.join()` - изчаква нишката да завърши
- `t.detach()` - отделя нишката да работи самостоятелно (рядко е нужно)
- `ref(променлива)` - подава аргумент по референция (без него нишката получава копие и функция с параметър по референция не се компилира)

*Пример: първа нишка*

```cpp
#include <iostream>
#include <thread>
using namespace std;

void hello() {
    cout << "Hello from the thread!" << endl;
}

int main() {
    thread t(hello);   // нишката стартира веднага
    t.join();          // главната нишка изчаква t да завърши
    cout << "End of the program" << endl;
}
```

*Пример: няколко нишки с аргумент*

```cpp
#include <iostream>
#include <thread>
#include <vector>
using namespace std;

void worker(int id) {
    cout << "Thread " << id << " is working" << endl;
}

int main() {
    vector<thread> threads;
    for (int i = 1; i <= 5; i++)
        threads.emplace_back(worker, i);   // създава и стартира нишка

    for (thread &t : threads)
        t.join();                          // изчаква всички
}
```

Изходът от няколко нишки може да е разбъркан (например думите на два реда да се преплетат) и редът на нишките не е гарантиран - той се променя от изпълнение на изпълнение. Това е нормално и е причината да е нужна синхронизация.

*Пример: връщане на резултат през референция и lambda*

```cpp
#include <iostream>
#include <thread>
using namespace std;

void square(int n, int &result) {
    result = n * n;
}

int main() {
    int result = 0;
    thread t(square, 7, ref(result));   // ref - подаване по референция
    t.join();
    cout << "7 squared is " << result << endl;

    thread t2([] { cout << "Lambda thread example" << endl; });
    t2.join();
}
```

### 2. Времена на заспиване

`this_thread::sleep_for(...)` приспива **текущата** нишка за зададено време. През това време нишката не заема процесор, а останалите нишки продължават да работят. Времето се задава с литерали от `<chrono>`: `500ms` (милисекунди), `2s` (секунди), `1min` (минута).

Заспиването е най-важният помощник в това упражнение, защото:

- **симулира работа** - реалните задачи отнемат време, а нашите примери са твърде бързи;
- **прави преплитането видимо** - виждаме коя нишка кога се събужда;
- **прави проблемите възпроизводими** - със заспиване на подходящо място състезанието и мъртвата хватка се получават всеки път, а не „понякога“.

Важно правило: заспиването **не е синхронизация**. Никога не използвайте `sleep_for`, за да „изчакате“ друга нишка да свърши - за това служи `join()`.

**Основни средства:**

- `this_thread::sleep_for(500ms)` - заспива за зададено време
- `this_thread::sleep_until(момент)` - заспива до определен момент във времето
- `this_thread::yield()` - отстъпва процесора на друга нишка
- `chrono::steady_clock::now()` - текущо време, за измерване на продължителност

*Пример: две нишки с различно време на заспиване, с измерване на времето*

```cpp
#include <iostream>
#include <thread>
#include <chrono>
using namespace std;

void tik() {
    for (int i = 0; i < 3; i++) {
        cout << "тик" << endl;
        this_thread::sleep_for(500ms);
    }
}

void tak() {
    for (int i = 0; i < 3; i++) {
        cout << "    так" << endl;
        this_thread::sleep_for(800ms);
    }
}

int main() {
    auto start = chrono::steady_clock::now();

    thread a(tik), b(tak);
    a.join();
    b.join();

    auto end = chrono::steady_clock::now();
    auto ms = chrono::duration_cast<chrono::milliseconds>(end - start).count();
    cout << "Total time: " << ms << " ms" << endl;   // около 2400, не 3900
}
```

Общото време е около 2400 ms (колкото най-бавната нишка), а не сбор от двете (1500 + 2400), защото нишките заспиват **едновременно**. Това е и основната идея на нишките - работата се припокрива във времето.

### 3. Състезание на нишки (race condition)

Състезание възниква, когато две или повече нишки едновременно четат и променят една и съща променлива и крайният резултат зависи от реда, в който се редуват. Дори `counter++` не е една неделима стъпка, а три:

1. прочети `counter` в временна променлива;
2. увеличи временната променлива с 1;
3. запиши обратно в `counter`.

Ако между стъпки 1 и 3 другата нишка също прочете `counter`, и двете ще запишат една и съща нова стойност и едно увеличаване се „губи“ (lost update). Състезанието е коварно, защото при бързи програми често не се проявява и програмата изглежда правилна. С помощта на заспиване (стъпка 2 „отнема време“) го правим видимо всеки път.

*Пример: състезание - грешният резултат се получава всеки път*

```cpp
#include <iostream>
#include <thread>
#include <chrono>
using namespace std;

int counter = 0;                       // споделена променлива, НЕзащитена

void increment() {
    for (int i = 0; i < 100; i++) {
        int tmp = counter;             // 1. чете
        this_thread::sleep_for(1ms);   // 2. "работи" - другата нишка се намесва
        counter = tmp + 1;             // 3. записва
    }
}

int main() {
    thread a(increment), b(increment);
    a.join();
    b.join();
    cout << counter << " (expected 200)" << endl;
}
```

Очаква се резултат значително по-малък от 200 (при изпробване - около 100), въпреки че всяка нишка е направила по 100 увеличавания. Точната стойност зависи от машината, но почти никога не е 200.

**Практическа бележка:** ако премахнете `sleep_for` и увеличите итерациите до милиони, състезанието пак съществува, но на виртуална машина с **едно** ядро може да не се прояви в повечето изпълнения (нишките рядко се прекъсват точно в тесния прозорец). Затова за демонстрации се използва заспиване. В C++ състезанието е и формално **недефинирано поведение** - не само „грешен резултат“, а програма без гарантирано поведение.

### 4. Синхронизация на нишки

Синхронизацията гарантира, че критичната секция (участъкът, който пипа споделени данни) се изпълнява от една нишка в даден момент. Два основни инструмента:

**`mutex` (взаимно изключване)** - „ключалка“, която само една нишка може да държи. Класът `lock_guard` заключва мютекса при създаването си и го отключва автоматично, когато излезе от блока `{ }` - дори при `return` или изключение. Затова се предпочита пред ръчните `m.lock()` / `m.unlock()`, при които забравено `unlock()` блокира всички останали нишки завинаги.

**`atomic`** - тип, чиито операции са неделими. За прост брояч `atomic<int>` е най-лесното и най-бързото решение, без изрична ключалка. Защитава само **една** променлива; когато няколко променливи трябва да се променят заедно, е нужен мютекс.

**Основни средства:**

- `mutex m;` - мютекс (заглавен файл `<mutex>`)
- `lock_guard<mutex> lock(m);` - заключва до края на блока
- `atomic<int> x;` - атомарна променлива (заглавен файл `<atomic>`)
- `unique_lock<mutex>` - по-гъвкава ключалка (може да се отключва ръчно)

*Пример: състезанието от предишния пример, поправено с `mutex`*

```cpp
#include <iostream>
#include <thread>
#include <mutex>
#include <chrono>
using namespace std;

int counter = 0;
mutex m;

void increment() {
    for (int i = 0; i < 100; i++) {
        lock_guard<mutex> lock(m);     // заключва; отключва се в края на итерацията
        int tmp = counter;
        this_thread::sleep_for(1ms);
        counter = tmp + 1;
    }
}

int main() {
    thread a(increment), b(increment);
    a.join();
    b.join();
    cout << counter << " (expected 200)" << endl;   // винаги 200
}
```

Забележете, че програмата вече е по-бавна: докато една нишка държи мютекса (и спи), другата чака. Колкото по-дълго се държи ключалката, толкова по-малко полза от нишките - затова критичната секция трябва да е възможно най-кратка. Тук заспиването вътре в нея е само за демонстрация.

*Пример: брояч с `atomic`*

```cpp
#include <iostream>
#include <thread>
#include <atomic>
#include <vector>
using namespace std;

atomic<int> counter(0);

void increment() {
    for (int i = 0; i < 1000000; i++)
        counter++;                     // атомарно увеличаване, без ключалка
}

int main() {
    vector<thread> threads;
    for (int i = 0; i < 4; i++)
        threads.emplace_back(increment);
    for (thread &t : threads)
        t.join();

    cout << counter << " (expected 4000000)" << endl;   // винаги 4000000
}
```

*Извън обхвата на това упражнение:* чакане на събитие (`condition_variable`) и семафори (C++20) не се разглеждат тук.

### 5. Мъртва хватка (deadlock)

Мъртва хватка възниква, когато две или повече нишки чакат една друга завинаги. Класически пример: нишка A държи ключалка 1 и чака ключалка 2, а нишка B държи ключалка 2 и чака ключалка 1. Нито една не може да продължи. Програмата „увисва“ - не дава грешка и не завършва.

Четирите условия, които трябва да са изпълнени **едновременно**, за да възникне мъртва хватка (условия на Coffman):

1. **взаимно изключване** - ресурсът се ползва от една нишка наведнъж;
2. **задържане и чакане** - нишката държи един ресурс и чака друг;
3. **без отнемане** - ресурсът не може да бъде отнет насила;
4. **кръгово чакане** - A чака B, а B чака A.

Достатъчно е да се наруши **едно** от тях. Най-често се нарушава кръговото чакане: (а) всички нишки заключват мютексите в **един и същ ред**, или (б) заключват и двата наведнъж със `scoped_lock` (C++17), който избягва мъртва хватка независимо от реда.

Заспиването прави мъртвата хватка възпроизводима: като приспим нишката A за 100 ms след първата ключалка, даваме време на B да вземе втората - и хватката се получава всеки път.

Как се разпознава: програмата спира да печата, а процесорът е на 0% (нишките не въртят в цикъл, а чакат). С `Ctrl+C` се прекратява; с `top -H -p <PID>` или `gdb -p <PID>` (`thread apply all bt`) се виждат нишките, блокирани в `lock`.

*Пример: мъртва хватка (програмата няма да завърши - прекратете я с Ctrl+C)*

```cpp
#include <iostream>
#include <thread>
#include <mutex>
#include <chrono>
using namespace std;

mutex m1, m2;

void threadA() {
    lock_guard<mutex> l1(m1);
    cout << "A took m1" << endl;
    this_thread::sleep_for(100ms);     // време за B да вземе m2
    lock_guard<mutex> l2(m2);          // чака B... завинаги
    cout << "A took both" << endl;
}

void threadB() {
    lock_guard<mutex> l2(m2);
    cout << "B took m2" << endl;
    this_thread::sleep_for(100ms);     // време за A да вземе m1
    lock_guard<mutex> l1(m1);          // чака A... завинаги
    cout << "B took both" << endl;
}

int main() {
    thread a(threadA), b(threadB);
    a.join();
    b.join();
    cout << "This message is not going to be shown" << endl;
}
```

*Поправка 1: еднакъв ред на заключване* (и двете нишки първо m1, после m2)

```cpp
void threadA() {
    lock_guard<mutex> l1(m1);
    this_thread::sleep_for(100ms);
    lock_guard<mutex> l2(m2);
    cout << "A took both" << endl;
}

void threadB() {
    lock_guard<mutex> l1(m1);          // същият ред като при A
    this_thread::sleep_for(100ms);
    lock_guard<mutex> l2(m2);
    cout << "B took both" << endl;
}
```

*Поправка 2: `scoped_lock` заключва двата мютекса наведнъж*

```cpp
void threadA() {
    scoped_lock lock(m1, m2);          // C++17; безопасно, редът няма значение
    this_thread::sleep_for(100ms);
    cout << "A took both" << endl;
}

void threadB() {
    scoped_lock lock(m2, m1);          // обратен ред - пак безопасно
    this_thread::sleep_for(100ms);
    cout << "B took both" << endl;
}
```
